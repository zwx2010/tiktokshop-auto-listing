## Critical issues

1. **No runnable persistent worker is wired for production-created API tasks.**  
   `app/main.py:18` creates the API with no `start_worker`, while `app/api/app.py:22-24` only starts a worker if an external callable is explicitly supplied. `PersistentTaskWorker` has no executable/service entry point in this change. Thus a task accepted by the production API remains `pending` indefinitely; the test only manually instantiates a worker in the same test process. This fails W1's completion criterion that tasks created by the API can be consumed by an independent worker. Add and document a separately runnable worker process using the same `SessionLocal`/MySQL configuration, then test that process/service boundary (or its callable entry point) against the production repository wiring.

## Important issues

1. **The mandatory MySQL and restart-recovery evidence is absent.**  
   `tests/test_api_lifecycle.py:53-59` deliberately uses an in-memory SQLite `StaticPool`, and `tests/test_api_lifecycle.py:72-80` performs one immediate worker run; it neither verifies the MySQL repository nor simulates an API/worker restart. The execution contract's W1 test obligation explicitly requires “API→MySQL worker、重启恢复”. Add a MySQL integration test (appropriately gated by test configuration) that creates through the API, creates fresh worker/repository instances after restart, and verifies the persisted task is consumed once.

2. **The added fallback bypasses image quality validation without regression coverage.**  
   `tools/export_platform_to_staging.py:328-330` returns all source URLs when the optional vision helper is absent. That changes the established `filter_small_images` contract immediately below it (unparseable images are filtered and must still be caught by the upload gate), potentially exporting undersized/invalid images. Either prove the downstream gate always blocks these rows and add coverage, or retain an explicit failing/review status rather than silently treating unverified images as usable.
