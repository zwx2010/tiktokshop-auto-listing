# 生产基础加固与飞书运营控制面

## Why

当前项目同时存在内存任务服务、MySQL 任务仓储和内存审批状态机：`/api/v1/tasks` 创建的任务不能保证被 MySQL worker 消费，进程重启会丢失审批上下文。飞书多维表格已可领取和锁定待上架行，但没有以数据库任务和审计记录为事实源的完整运营闭环。回调及采集日志还可能记录原始载荷，扩大了令牌和个人标识泄露风险。

## What Changes

- 以 MySQL `tasks`、`task_logs` 和审批审计记录统一任务、审批和恢复机制。
- 让飞书多维表格成为运营控制面：选品、批次、门禁、人工批准、重试和发布结果均通过受控字段回写。
- 使用原子领取/租约与幂等键防止多 worker、重试和飞书重复回调造成重复发布。
- 保留本地看板，但只提供健康、任务和集成诊断；移除运营性操作入口。
- 对飞书、AI、CDP、TikTok 分阶段进行真实连通验证；验证完成后，生成不超过约 50 件测试商品的发布清单，必须经过独立人工批准才可提交。
- 将现有未提交的图片、价格和导出兼容修复纳入回归测试和本期交付。

## Scope

### In

- MySQL 任务/审批持久化、并发领取、租约恢复、可审计日志与脱敏。
- 飞书多维表格的字段契约、状态机、批次隔离、审批动作和结果回写。
- 飞书、AI、CDP、TikTok 的非发布连通验证与发布前人工批准门。
- 只读诊断页、运行手册、数据库迁移与自动化回归。

### Out

- 自建运营前端和前端原型。
- 改变采集、清洗、定价、三站本地化与既有商品规则。
- 未经人工批准的真实发布、批量超过约 50 件的测试发布。

## Impact

影响 `app/api/`、`app/application/`、`app/infrastructure/`、`app/agent/`、`app/feishu/`、`app/routers/`、`app/models.py`、迁移、worker、测试和部署文档。飞书多维表格字段是对运营人员公开的兼容边界；数据库任务状态是唯一的执行事实源。

## Proof of Completion

- API 创建的任务可被重启后的 MySQL worker 消费，且并发 worker 只会领取一次。
- 飞书行的状态、批次、门禁和结果可追溯到数据库任务与审计记录。
- 同一审批回调、重试或租约恢复不会重复创建发布动作。
- 四类集成的连通结果均包含真实时间、请求范围、结果与失败原因；发布动作需显式批准并限制测试数量。
- 日志和 API 诊断不输出令牌、签名、完整回调体或个人标识；全量自动化测试和迁移验证通过。
